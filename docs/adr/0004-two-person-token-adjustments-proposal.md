# 提案：游戏 Token 管理员调整采用双人审批

状态：后端和运营页面已本地实现，拟任独立审批人待本人确认（2026-09-27）

## 背景

[MVP 完成定义](../../plan.md#17-mvp-明确完成定义)要求 Token 的管理员调整可审计。`ledger_events` 只能追加、不能更新或删除；本方案补充受控的管理员调整入口。仅靠维护者直接写数据库既无法证明双人复核，也无法把调整与理由稳定关联。

## 提议

1. 第一版只允许调整游戏内 `token`，不调整真实模型用量、修为或功德。
2. 现有 `MAINTAINER_GITHUB_ID` 对应账号提出申请；另设 `FINANCE_APPROVER_GITHUB_ID` 对应账号批准或驳回。两者缺失或相同，调整入口关闭；申请人不能批准自己的申请。
3. 单笔 `delta` 为非零整数，暂定绝对值不超过 10,000 Token。申请必须填写 20–500 字理由和在目标修士内唯一的业务引用；重复引用不产生第二笔申请。
4. 申请保存为待审批记录。批准时只允许一次从「待审批」转为「已批准」，并在同一数据库事务中追加一笔以申请 ID 为来源键的 Token 流水；驳回不产生流水。负余额约束仍生效，扣减失败则审批回滚。
5. 申请、决定人、决定理由和时间保留在数据库，不允许通过产品接口修改或删除历史记录。对账页需能区分管理员调整与普通奖励、消费和退款。

后端迁移、申请/审批接口和 `/economy` 操作页面已在本地实现，但不是已上线能力。主理人指定 [@Gjts](https://github.com/Gjts) 为拟任第二审批人；公开 GitHub 资料显示其数字 ID 为 `45388369`，与 [@HardieBao](https://github.com/HardieBao) 的 `134252261` 不同。尚无 @Gjts 本人接受职责和独立签署的证据，不在生产环境配置审批 ID，管理员调账入口保持关闭。10,000 Token 上限与业务引用格式如需调整，应同时更新迁移、接口、测试和运营说明。

## 权衡

- 单人调账再事后审计实现更快，但不能阻止同一账号自批，不满足双人复核目标。
- 通用 RBAC、任意数量财务审批人与复杂额度分级更灵活，但在当前单维护者 Pre-Alpha 中增加了配置与审查面；先采用两名明确指定账号。
- 直接修改余额或历史流水被排除；所有经济变化仍必须通过追加事件表示。

## 验证边界

本地已从申请/审批 API 与隔离 D1 账本事务验证：自批拒绝、重复批准不重复铸币、扣减不能造成负余额、驳回不写流水；纯函数测试覆盖配置缺失和同一 GitHub ID 时关闭入口。2026-09-27 以合成账号完成页面→API→D1→页面验证：申请人无审批按钮，审批人无申请入口和全账号对账数据；普通账号读取 API 返回 403。批准 +25 后余额从 100 变为 125 且只追加一笔流水；驳回 +10 不改账；批准 -126 返回 409，决定和流水全部回滚，复核理由保留。手机 500 字理由确认框可滚动且按钮可达。尚缺两个真实 GitHub 账号的部署后演练与生产对账，合成账号不能代替本人接受职责或签署。
